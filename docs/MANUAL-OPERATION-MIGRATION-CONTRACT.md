# Контракт 1С-сторонней миграции ручной операции

Дата: 2026-11-13. Статус: **синтетический проект контракта**, не установка и
не проверка на живой базе. Рабочие документы и банковские данные не
использовались.

## 1. Что требуется перенести

Одна ручная операция (`Document_ОперацияБух`) и набор движений одного
регистратора `AccountingRegister_Хозрасчетный`:

- `Posted` документа и `Active` каждой записи переносятся независимо и явно;
- счета Дт/Кт и до трёх пар типизированного субконто с каждой стороны;
- пустые суммы, ссылки и аналитика остаются пустыми — значения по умолчанию не
  подставляются;
- шапка и движения записываются атомарно; после записи выполняется чтение и
  сверка; при расхождении — откат всей транзакции;
- ключ повторяемости защищает от дубля при повторе запроса.

Машинно-читаемый контракт: [`prototype/1c-migration-operation/contract.json`](../prototype/1c-migration-operation/contract.json).
Эскиз BSL: [`prototype/1c-migration-operation/OperationMigration.bsl`](../prototype/1c-migration-operation/OperationMigration.bsl)
(не компилировался; содержит `TODO` для непроверенного API движений).

## 2. Требования 1С:Фреш, которые нужно соблюсти

По [опубликованным требованиям 1С:Фреш к дополнительным отчётам и обработкам](https://1cfresh.com/articles/so_addprocess_req):

- обработка должна быть внешней обработкой `.epf`, разработанной по
  требованиям подсистемы БСП «ДополнительныеОтчетыИОбработки»;
- `СведенияОВнешнейОбработке()` должен явно задавать безопасный режим;
  не разрешённые в нём операции требуют отдельных разрешений
  `РаботаВБезопасномРежиме`;
- нельзя использовать COM, внешние компоненты вне конфигурации, обфускацию или
  закрытые модули; код должен быть доступен аудиту;
- обработка не должна выходить в сеть и передавать данные за пределы сервиса
  без явного подтверждения пользователя;
- длительные операции — через механизм длительных операций БСП; действуют
  ограничения на серверный вызов, память и запись на диск;
- тестирование — на той же версии платформы и конфигурации, что в сервисе,
  под пользователями с ролями без полных прав, в тонком и веб-клиенте (если
  есть формы).

Связанные документы: [обязательство по разработке](https://www.1cfresh.com/resources/images/content/articles/so_addprocess_dev/obligation.pdf),
[форма заявки](https://www.1cfresh.com/resources/images/content/articles/so_addprocess_dev/application.pdf).

## 3. Доступные в проекте средства BSL

В репозитории **нет** компилятора, линтера или тест-раннера BSL, и нет
установленного 1С:Конфигуратора/EDT. `package.json` содержит только
TypeScript/ESLint/Prettier/Vitest. Поэтому:

- BSL-эскиз не компилируется в этом репозитории и не считается проверенным;
- синтетический тест проверяет только контракт и наличие обязательных
  инвариантов в тексте, а не исполнение BSL;
- для реальной проверки нужна отдельная среда 1С:Конфигуратор/EDT или
  сертифицированный BSL-инструмент, которого в проекте нет.

## 4. Штатный интерфейс для первой операции

Предпочтительный путь — стандартный объектный API
`Документы.ОперацияБух` и его штатный механизм движений. Перед реализацией
владелец/обслуживающая организация должны подтвердить на тестовой базе:

1. есть ли у `ОперацияБух` опубликованная/доступная табличная часть проводок
   или другой штатный объектный API, записывающий движения **непроведённого**
   документа;
2. можно ли записать движения одного регистратора, не выполняя проведение и не
   меняя `Posted` на `true`;
3. разрешены ли эти операции в безопасном режиме и под тестовыми ролями;
4. как выглядит точный состав полей субконто и их видов в этой версии
   конфигурации.

Если такого API нет, прототип **не применяется**: запись напрямую в таблицы
регистра или обход штатного API не допускается. Нужен отдельный согласованный
1С-сторонний сценарий (расширение/сервис) с теми же гарантиями.

## 5. Инварианты контракта

| Инвариант | Требование |
|---|---|
| Атомарность | Шапка и все движения одного регистратора в одной транзакции; при любой ошибке — откат. |
| Повторяемость | `sourceKey` + ограниченный поиск по организации/номеру/году; повтор возвращает существующий документ, не создаёт второй. |
| `Posted`/`Active` | Не выводятся друг из друга; `Posted=false` возможен при активных движениях. |
| Ссылки | Существование, отсутствие пометки удаления и точный тип; неразрешённая ссылка — отказ до записи. |
| Субконто | Для каждого использованного слота обязательны ссылка и вид; пустой слот остаётся пустым. |
| Суммы | Сумма строки, Дт/Кт и заданные налоговые суммы сверяются точно; пустые не заменяются нулём. |
| Чтение | После записи документ и все записи по регистратору перечитываются; сверяются все переданные поля. |
| Откат | Несовпадение readback/типа ссылки/суммы откатывает транзакцию; частичных шапки/движений не остаётся. |

## 6. Тестовый сценарий rollback

Синтетический сценарий из `contract.json`:

1. открыть транзакцию;
2. записать шапку с `Posted=false` и одну активную строку с типизированным
   субконто и пустыми налоговыми суммами;
3. намеренно подменить вид субконто/ссылку в проверяемых данных;
4. выполнить readback и получить несовпадение;
5. отменить транзакцию;
6. проверить: документа нет, записей регистратора нет, повтор с тем же ключом
   не создаёт дубль.

Проверка выполняется только на синтетической тестовой базе; production не
используется.

## 7. Что нужно от владельца/обслуживающей организации

До реализации и установки нужны:

- тестовая информационная база той же платформы и версии конфигурации, что в
  сервисе, с включёнными дополнительными обработками;
- тестовый пользователь с ролями, достаточными для записи документа/движений,
  но без полных прав; отдельно — подтверждение работы в безопасном режиме;
- подтверждение штатного API движений и точных имён полей субконто в этой
  версии конфигурации;
- синтетические организация, контрагент, счета, субконто и их виды;
- разрешение на запуск обработки в тестовом контуре и возможность отката
  тестовых данных;
- отсутствие требования устанавливать обработку в рабочую базу до отдельного
  согласования.

## 8. Применимость

Прототип применим только если:

- целевая конфигурация публикует/разрешает объектный API движений
  непроведённого `ОперацияБух`;
- безопасный режим и роли позволяют эту запись;
- владелец подтвердил тестовый контур и состав реквизитов.

Иначе первая операция через штатный интерфейс невозможна; нужен отдельный
1С-сторонний сервис/расширение, и этот прототип остаётся только проектом
контракта.
