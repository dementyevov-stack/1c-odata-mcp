# Исторический счёт-фактура выданный: контракт и граница доказательства

Статус: клиентская часть и синтетические регрессии; серверная причина HTTP 500
не воспроизводилась и не исправлялась.

## 1. Выбранная база

Работа начата от `0d977d33d34da4131e49344490980d7c693b5b85` (проверенный SHA
PR #12). На этой базе `write.sales.create_issued_invoice` действительно задавал
`ВидСчетаФактуры=НаРеализацию`, дату без времени и не имел исторического
`Number`. Это подтверждённый клиентский пробел, но **не** доказанная причина
внешнего HTTP 500.

## 2. Что добавлено

Opt-in исторический режим:

- явные `number`, `time`, `issueDate`, `issueTime`;
- явный `invoiceKind` (`НаРеализацию`/`НаАванс`), без вывода аванса из ссылки
  на банковский документ;
- явный `operationCode`;
- `basisDocuments`: типизированные `ref`/`type`, номер/дата исходного
  документа, несколько строк;
- `paymentDocuments`: платёжно-расчётные документы для аванса;
- `ДокументыОснования[i].considerCorrection=false` — явный
  `УчитыватьИсправлениеИсходногоДокумента`, сохраняется и проверяется;
- `emptyShipmentDocuments=[]` и `emptyCorrectableLineNumbers=[]` передают
  явно пустые опубликованные таблицы; omission не равен явной пустоте;
- `paymentDocuments[].date`/`invoiceDate` принимают `YYYY-MM-DD` или
  `YYYY-MM-DDTHH:MM:SS`; полное время сохраняется, дата без времени получает
  канонические `T00:00:00`;
- `advanceRows`: обязательная историческая таблица «Авансы» для `НаАванс`
  (номенклатура, содержание, сумма, ставка/НДС, типизированное основание,
  номер/дата платёжно-расчётного документа, продавец/корректировка,
  контрагент; zero GUID допустим как явная пустота);
  `basisRef` и `basisType` — только парой, основание должно входить в
  `basisDocuments`; для аванса обязательны явные `sumTotal`/`sumVat`, потому
  что VAT из банковского основания не выводится;
- `sumTotal`/`sumVat` — явные суммы `СуммаДокумента`/`СуммаНДСДокумента`,
  иначе из основания; отдельные `sum`/`vat` — физические `Сумма`/`СуммаНДС`;
- allowlisted шапка: `contractRef`, `currencyRef`, `responsibleRef`,
  `chiefAccountantRef`, `invoiceForPaymentRef`, `comment`,
  `numberRepresentation`, `headerPaymentNumber`, `headerVatRate`,
  `headerPaymentDate`, `issued`, `invoiceNotIssued`, `invoiceWithoutVat`,
  `manualCorrection`, `correction`, `sub0`, `initialBalanceVat`,
  `representationMethod`; типы/ссылки проверяются по метаданным, false/0/
  пустая строка/zero GUID сохраняются;
- пустые таблицы передаются явно (`paymentDocuments: []`), отсутствующие поля
  не превращаются в пустоту;
- `advanceRows[i].counterpartyRef=00000000-...` — допустимая явная пустота;
  непустой другой контрагент по-прежнему отклоняется;
- исторический `Комментарий` не получает служебную метку операции и не
  обрезается даже при включённой метке; recovery идёт по operationId/Ref_Key;
- обычный режим без новых полей сохранён;
- перед POST выполняется точный поиск по организации/типу/году/номеру;
  существующая запись, неоднозначность или неполный поиск блокируют POST;
- номера строк оснований нормализуются до проверки уникальности;
- readback-failed сохраняется в журнале, и повтор operationId возвращает
  failed/pending, а не мнимый успех; квитанция до readback атомарно создаётся
  как pending, так что сбой записи журнала после POST не открывает успех.
  `DeletionMark=false` — readback-предусловие, в payload не отправляется:
  документ создаётся непроведённым, а серверный false проверяется после POST.
  `pending` входит в `summary().uncertain`, а старые квитанции этого профиля
  без verification считаются unverified, не ok; новые обычные квитанции имеют
  явный `verificationRequired=false` и replay-ятся как receipt-only.

Readback проверяет номер, обе даты/время, вид, код, основания (тип/ссылку/
строку), платёжно-расчётную таблицу, суммы/НДС, `Posted`/`DeletionMark`.
Пропуск обязательного поля или расхождение — `verification: failed`.

## 3. Диагностика и неизвестный исход

При ошибке POST возвращается:

- стадия (`POST`), профиль `historical-issued-invoice`, `entitySet`;
- `errorKind`, HTTP-статус, `retryable`, имя cause-класса (без тела с данными);
- `operationId` и `outcome` (`unknown` или `possibly_created`);
- безопасная цепочка cause (класс/kind/status, без тела с данными);
- выборка контрагента основания строится по фактическим метаданным:
  `Контрагент_Key` либо `Контрагент`+`Контрагент_Type`; отсутствие поля —
  отказ, а не пропуск проверки;
- результат точного поиска: `none`, `found`, `ambiguous`, `incomplete`,
  `unavailable`; только `found` даёт `possibly_created`, остальные — unknown.

HTTP 500/потеря ответа не считаются безопасным отказом. 404 на чтение сам по
себе не доказывает отсутствие эффекта; поиск при неполноте/неоднозначности не
разрешает новый POST. Повтор с тем же `operationId` не создаёт второй документ.
Автоматических повторных POST и перебора payload нет.

## 4. Что не доказано

Причина HTTP 500 «Не удалось записать: Счёт-фактура выданный» в наблюдении
неизвестна. Синтетический mock 500 проверяет только диагностику клиента и не
воспроизводит поведение 1С. Не доказаны и не заявлены:

- исправление серверной причины или работоспособность прямого POST;
- права, публикация, бизнес-проверки конфигурации, обязательные зависимости
  или серверный обработчик;
- корректность штатного сохранения формы «создать на основании».

## 5. Минимальная проверка в разрешённой тестовой базе

На тестовой базе той же версии платформы/конфигурации, под тестовым
пользователем, без рабочих данных:

1. Выполнить GET основания и сохранить точные `Ref_Key`, тип, суммы/НДС.
2. Выполнить штатное «создать на основании» для обычной реализации и для
   аванса; **не сохранять** форму — зафиксировать заполненные реквизиты и
   доступные таблицы.
3. Выполнить один исторический POST с `confirm=true` и тем же набором полей,
   но только синтетическими ссылками/суммами. Зафиксировать HTTP-статус, тело
   ошибки (в закрытом журнале, не в GitHub) и `operationId`.
4. Сразу выполнить точный GET/поиск по номеру+организации+году и
   `write.operation.status`; отдельно — GET назначенного GUID.
5. Сравнить с шагом 2: какие реквизиты/таблицы форма заполняет, а прямой
   payload не передаёт; какие обязательные зависимости видны только в форме.

Факт, различающий гипотезы: если штатное сохранение «на основании» создаёт
документ с тем же набором полей, а прямой POST стабильно 500 при точном
readback-совпадении, причина — в серверном обработчике/обязательных
зависимостях или правах, а не в отсутствии клиентского `Number`/времени.
Если прямой POST успешен после добавления конкретного поля — это доказывает
недостающее поле, но не «исправление 500» вообще.

Иной штатный механизм (например, серверное создание на основании) допустим
только после подтверждения его интерфейса; произвольный BSL-execute, ручная
запись регистров вместо СФ или обход бизнес-проверок не используются.
