# Загрузчик банковских документов БП: первый участок

Операторский путь для оплаты покупателя документом **«Поступление на расчётный счёт»**. Это не
автоматическая замена бухгалтера: загрузчик готовит документы, показывает план, пишет только по
явному подтверждению и оставляет журнал для повторного запуска. Реальный пакет выписки оператор
запускает после приёмки на синтетических данных.

Загрузчик работает через штатный stdio MCP-сервер. Поэтому подготовка, проверка `$metadata`,
предпросмотр, `operationId`, журнал записи и сверка после потерянного ответа — те же, что у обычного
MCP-клиента; отдельной копии правил записи нет.

## Что проверяется до записи

1. **GET схемы и организации.** `diagnose` вызывает `read.system.health_check` — авторизованный GET
   `$metadata` — и `read.system.list_organizations` с точными ИНН/КПП.
2. **Точная сверка, а не догадка.** Список организаций, контрагентов и банковских счетов читается
   страницами до предела. Фильтр по ИНН на стороне 1С — только ускорение: публикация может ответить
   HTTP 500, тогда выполняется ограниченный полный проход и локальная сверка. `$top=1` не
   используется: одна строка не доказывает единственность. При обрыве предела или двух совпадениях —
   отказ, а не «первая подходящая».
3. **Счёт именно организации.** В справочнике «Банковские счета» владелец полиморфный: `Owner` +
   `Owner_Type`. Для счёта организации `Owner_Type = StandardODATA.Catalog_Организации`, для счёта
   контрагента — `StandardODATA.Catalog_Контрагенты`. `read.organization.find_bank_account` и
   `write.organization.create_bank_account` проверяют именно владельца-организацию и никогда не
   выдают счёт контрагента за счёт организации. Основной счёт организации этот путь не меняет:
   `ОсновнойБанковскийСчет_Key` назначается в 1С осознанно.
4. **Явные поля источника.** Ставка и сумма НДС (включая исторические `НДС18`, расчётные ставки),
   назначение платежа, номер и дата входящего банковского документа, счёт плательщика переносятся,
   только если поле опубликовано в схеме. Если поле не опубликовано или контрольное чтение после
   создания не совпало — отказ с диагностикой; молчаливой потери данных нет. НДС задаётся **парой**
   (ставка + сумма): одну величину загрузчик не угадывает. Без явного НДС выставляются `БезНДС` и 0,
   как у обычной оплаты покупателя.
5. **Счета расчётов и договор.** Договор ищется по точному номеру или единственному подходящему у
   контрагента; несколько подходящих — отказ. Счета расчётов и авансов подбираются той же политикой
   MCP, что и у `write.money.create_payment` (регистр «Счета учёта расчётов с контрагентами»), и
   видны в предпросмотре.

## Локальная конфигурация

Файл `bank-loader.json` лежит вне Git; адрес, логин, пароль и целевые реквизиты оператор задаёт
локально. Пароль лучше держать в переменной окружения, а не в файле.

```json
{
  "odata": {
    "baseUrl": "https://<сервер>/<база>/odata/standard.odata/",
    "usernameEnv": "ODATA_USERNAME",
    "passwordEnv": "ODATA_PASSWORD",
    "writeJournalDir": "~/.1c-odata-mcp/write-journal"
  },
  "target": {
    "organizationInn": "<ИНН организации: 10 или 12 цифр>",
    "organizationKpp": "<КПП организации: 9 цифр>",
    "bankAccountNumber": "<номер счёта организации: 20 цифр>",
    "bankBik": "<БИК банка организации: 9 цифр, нужен только для создания счёта>"
  },
  "journalDir": "~/.1c-odata-mcp/bank-loader"
}
```

`target.organizationKpp` можно не задавать для организации без КПП, но тогда ИНН должен быть
единственным. `target.bankBik` нужен только команде `ensure-account`, если счёта ещё нет.

## Пакет строк выписки

JSON-массив или объект `{ "documents": [...] }`; синтетический пример:

```json
{
  "documents": [
    {
      "sourceKey": "statement-2026-11-01-0001",
      "date": "2026-11-01",
      "amount": 1180.0,
      "payerInn": "<ИНН покупателя>",
      "payerKpp": "<КПП покупателя>",
      "payerName": "Синтетический покупатель",
      "payerAccountNumber": "<счёт плательщика, 20 цифр, если есть>",
      "purpose": "Оплата по договору",
      "documentNumber": "BANK-77",
      "documentDate": "2026-10-31",
      "vatRate": "НДС18",
      "vatAmount": 180.0,
      "contractNumber": "D-1"
    }
  ]
}
```

`sourceKey` — стабильный ключ строки источника. По нему загрузчик хранит связь с `Ref_Key` документа
и не создаёт дубль при повторе. Не переиспользуйте ключ для других данных после создания документа.

## Команды

```bash
npm ci
npm run build

# 1. Диагностика: авторизованный GET схемы, чтение организации, поиск её счёта.
node dist/scripts/bp-loader.js diagnose --config bank-loader.json

# 2. Если счёта организации нет — посмотреть/создать его.
node dist/scripts/bp-loader.js ensure-account --config bank-loader.json          # предпросмотр
node dist/scripts/bp-loader.js ensure-account --config bank-loader.json --confirm

# 3. Подготовка: dry-run по умолчанию, в 1С ничего не пишется.
node dist/scripts/bp-loader.js prepare --config bank-loader.json --source package.json > report.json

# 4. Запись — только после приёмки и просмотра плана.
node dist/scripts/bp-loader.js load --config bank-loader.json --source package.json --confirm

# 5. Возобновление: без --confirm только сверяет ранее отправленное, ничего не подтверждая.
node dist/scripts/bp-loader.js resume --config bank-loader.json --source package.json

# 5a. Возобновление с подтверждением уже подготовленных строк; новые строки resume не создаёт.
node dist/scripts/bp-loader.js resume --config bank-loader.json --source package.json --confirm

# Журнал: sourceKey, состояние, operationId, Ref_Key; без сумм и реквизитов источника.
node dist/scripts/bp-loader.js status --config bank-loader.json
```

`load` без `--confirm` — тот же предпросмотр, что `prepare`. `resume` без `--confirm` **ничего не
подтверждает**: он только сверяет неизвестные исходы через `write.operation.status`, показывает
подготовленные строки и пропускает новые. `resume --confirm` подтверждает уже подготовленные строки,
но только если текущий план совпадает с сохранённым отпечатком; новые строки он не создаёт.

Перед подтверждением загрузчик повторно готовит план и сравнивает его отпечаток (целевая база, ссылки
организации/счёта/контрагента/договора и payload) с тем, который оператор видел в `prepare`. Если
источник, цель или план изменились — отказ `blocked`, старый план не подтверждается: нужен новый
`prepare`. `load --confirm` без ранее сохранённого плана тоже отказывает и ничего не пишет. На уже
загруженном `sourceKey` изменение источника остаётся конфликтом.

После неизвестного POST, когда `write.operation.status` нашёл `Ref_Key`, загрузчик не
довольствуется фактом существования: он читает документ и сверяет значимые поля шапки и первую
строку «Расшифровки платежа» (организация, счёт, контрагент, договор, дата, Posted, сумма, НДС,
счета расчётов/авансов, назначение, входящий документ) с сохранённым планом и требует ровно одну
строку расшифровки. Расхождение фиксируется как `verification: failed`, но
повторный POST всё равно не выполняется. Код возврата: `0` — всё сопоставлено/создано,
`1` — есть отказ/блокер/расхождение, `2` — ошибка конфигурации или транспорта.

## Журнал и повторный запуск

Запускайте один процесс загрузчика на каталог журнала: запись журнала атомарна, но
межпроцессной блокировки нет — два одновременных прогона могут разойтись. `journalDir/source-journal.json`
(права `0600`) хранит отпечаток источника, `operationId`,
состояние, `Ref_Key`/номер и значимые поля проверенного плана (ссылки, суммы, НДС) — они нужны,
чтобы после неизвестного POST сверить найденный документ, а не только факт его существования.
Полных реквизитов источника (ИНН/КПП, наименований плательщика) в журнале нет; назначение
платежа и суммы входят в проверяемые поля плана. Состояния:

- `prepared` — был предпросмотр, подтверждение не отправлялось;
- `submitted` / `unknown` — подтверждение отправлено, ответ потерян; повтор POST запрещён, следующий
  запуск сначала вызывает `write.operation.status`;
- `created` — документ найден по назначенному `Ref_Key` и связан с `sourceKey`; повторный запуск его
  пропускает;
- `rejected` — отказ до записи; следующий запуск делает новый предпросмотр.

Если после создания контрольное чтение не совпало с явными полями источника, документ всё равно
фиксируется как `created` с `verification: failed`, чтобы повтор не создал дубль; оператор разбирает
расхождение в 1С и не запускает ключ как новую строку.

## Живая проверка оператором

1. Соберите точный SHA и проверки на нём: `git rev-parse HEAD`, затем `npm ci` и `npm run check`.
2. Заполните `bank-loader.json` реквизитами тестовой базы; пароль держите в переменной окружения.
3. `diagnose` должен вернуть `ok: true`, ожидаемые `organization.ref` и `account.found: true` с
   `ownerType: StandardODATA.Catalog_Организации`. Если `account.found: false` — выполните
   `ensure-account` (сначала без `--confirm`) и проверьте `ownerType` в ответе.
4. `prepare` на одной синтетической или тестовой строке: в ответе `mode: dry-run`, `action: dry_run`,
   в `plan.payload` — нужные организация, счёт, контрагент, договор, сумма, НДС и входящий документ;
   в 1С после этого запроса документов нет.
5. Только после приёмки: `load --confirm`, затем откройте документ в 1С и сверьте номер/дату, счёт
   организации, контрагента, договор, сумму, ставку и сумму НДС, назначение платежа. Повторный
   `load --confirm` должен вернуть `already_loaded` без нового документа.
6. Для проверки возобновления: `resume` без `--confirm` не должен создавать или подтверждать ничего;
   при искусственно потерянном ответе — `resume --confirm` должен найти документ по `Ref_Key`,
   сверить поля и не отправить второй POST.

Реальные реквизиты, суммы и выписки в Git не добавляются — только этот документ с placeholder-ами и
синтетические тесты.

## Границы покрытия

- Только 1С:Бухгалтерия предприятия 3.0 и только «Поступление на расчётный счёт» (оплата
  покупателя), одна организация и один банковский счёт на строку, рубли. Проведение документа не
  выполняется.
- Загрузчик не парсит банковскую выписку и не принимает реальные данные из Git: пакет готовит
  оператор. Живые реквизиты, пароли и бухгалтерские данные в репозиторий не попадают.
- Лимиты справочников (`ODATA_MAX_ROWS`) и страницы (`ODATA_PAGE_SIZE`) наследуются от MCP-сервера.
  При достижении предела загрузчик отказывает, а не строит догадку.
- Первый участок проверен на синтетических ответах поддельной 1С по снимку схемы БП 3.0. Живой
  пакет и реальные базы требуют приёмки оператора; в PR указаны выполненные проверки и их границы.
